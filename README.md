# xkeen-config-mihomo

Конфигурация mihomo для домашнего роутера: перехват портов делает xkeen, весь
отобранный трафик уходит в mihomo, а тот раскладывает его по группам — свой
выходной узел, коммерческую подписку, отдельный выход для Google. Здесь же
живёт проект самого узла.

Если вы пришли сюда, чтобы поднять себе такой же узел, а не разбираться в этой
конфигурации — вам нужен [**OWN-NODE.md**](OWN-NODE.md): готовый промпт для
Claude Code плюс замеры, объясняющие каждое его ограничение. Он самодостаточен и
ничего из этого репозитория не требует.

## Что где

| Путь | Что это |
|---|---|
| `config.yaml` | конфигурация mihomo целиком: группы, правила, узлы |
| `rules/` | списки доменов для `rule-provider`'ов |
| `node/` | свой выходной узел: объявление состояния и скрипты |
| `scripts/` | заливка на роутер, валидатор, гео-проба и фильтры для секретов |
| `port_proxying.lst` | порты, которые xkeen отдаёт в mihomo |
| `.secrets.yaml` | реальные значения секретов, в git не уходит |
| `OWN-NODE.md` | как поднять такой узел с нуля: промпт и замеры |

**`rules/*.yaml` — не локальные файлы, а живой источник.** Роутер тянет их по
URL с `raw.githubusercontent.com` из этого репозитория, поэтому правка вступает
в силу только после `git push`, а не после заливки `config.yaml`.

Иконки групп берутся из чужих репозиториев (`amatol`, `zxc-rv`) по URL —
локальных копий здесь нет и не нужно.

## Трафик

xkeen перехватывает перечисленные порты и отдаёт их mihomo на `redir-port 1080`
и `tproxy-port 1081`. Список портов задаётся на роутере одной командой и лежит
рядом в `port_proxying.lst`:

    xkeen -ap 80,443,8443,596:599,1400,2000-2300,3478,5222,19200-19400,46420,50000-51000

Панель управления mihomo — `http://192.168.1.1:9090` (zashboard). Через тот же
адрес удобно смотреть, что реально выбрано в группах:

    curl -s http://192.168.1.1:9090/proxies

## Залить на роутер

    scripts/deploy            проверить, залить, перечитать конфиг через API
    scripts/deploy --restart  то же, но через `xkeen -restart`

Сначала гоняет валидатор и `mihomo -t`, потом кладёт `config.yaml` в
`/opt/etc/mihomo/` (предыдущий остаётся рядом как `config.yaml.prev`) и просит
mihomo перечитать его без перезапуска. `--restart` нужен, когда меняются порты,
`external-controller`, слушатель DNS или `tun` — это читается только при старте.
Доступ по ключу на dropbear из Entware. Ключ кладётся один раз, и не через
`ssh-copy-id`: dropbear в Entware собран с патчем OpenWrt и для root читает
только `/opt/etc/dropbear/authorized_keys`, а на `~/.ssh/authorized_keys`
отказывает молча.

    ssh -p 222 root@192.168.1.1 'mkdir -p /opt/etc/dropbear && chmod 700 /opt/etc/dropbear \
      && cat >> /opt/etc/dropbear/authorized_keys && chmod 600 /opt/etc/dropbear/authorized_keys' \
      < ~/.ssh/id_ed25519.pub

## Проверить перед заливкой

    ruby scripts/validate.rb          локальный config.yaml
    ruby scripts/validate.rb --live   плюс сверка с роутером

Ловит то, что mihomo молча проглатывает: висячие ссылки на группы, мёртвые
провайдеры, перекрытие правил по порядку. Код возврата 1 = есть ошибки.

Проверить, что конфиг вообще примут, можно и настоящим движком:

    mihomo -t -d /tmp/mihomo-test -f config.yaml

Это единственный способ поймать опечатку в имени поля узла: валидатор смотрит
на структуру, а не на схему mihomo.

## Секреты

Ссылки на подписки и реквизиты своего узла не хранятся в репозитории. В
`config.yaml` на диске они настоящие — файл в таком виде и заливается на
роутер, — а в коммит уходит версия с плейсхолдерами. Подмена в обе стороны
делается фильтром git, править файл нужно как обычно.

**Важно:** править надо реальными значениями. Плейсхолдеры подставляет только
smudge-фильтр на checkout, поэтому вписанный руками `${NODE_S_IP}` останется
строкой и узел не поднимется. Исключение — реквизиты резидентского прокси
(`TR_RES_*`): они плейсхолдерами остаются и на диске, а подставляет их
`scripts/deploy` в момент отправки на роутер.

Реальные значения лежат в `.secrets.yaml` (в `.gitignore`). **Держите его копию
вне репозитория**: без него после свежего клона в `config.yaml` останутся
плейсхолдеры.

| Ключ | Что |
|---|---|
| `SUB_A` | ссылка на подписку |
| `SUB_B` | вторая подписка, убрана из конфига; ключ оставлен как единственная копия ссылки |
| `NODE_S_IP`, `NODE_S_UUID` | адрес своего узла и UUID роутера |
| `NODE_S_PBK_X`, `NODE_S_SID_X`, `NODE_S_PATH` | вход XHTTP |
| `NODE_S_PBK_V`, `NODE_S_SID_V` | вход Vision |
| `TR_RES_SERVER`, `TR_RES_USER`, `TR_RES_PASS` | резидентский прокси для PlayStation, см. ниже |

Реквизиты узла обновляются командой `./node/bin/client show router` — она
печатает готовый блок.

### Подключение на новой машине

Фильтры не переносятся клонированием, это локальная настройка git:

    git config filter.scrub-subs.clean  "ruby scripts/scrub.rb"
    git config filter.scrub-subs.smudge "ruby scripts/unscrub.rb"
    git config filter.scrub-subs.required true

Затем положить рядом `.secrets.yaml` с ключами из таблицы выше и обновить
рабочую копию: `rm config.yaml && git checkout config.yaml`.

### Как это устроено

| Файл | Роль |
|---|---|
| `scripts/scrub.rb` | clean-фильтр: секреты → плейсхолдеры, на `git add` |
| `scripts/unscrub.rb` | smudge-фильтр: плейсхолдеры → секреты, на checkout |
| `.gitattributes` | привязывает фильтр к `config.yaml` |

`scrub.rb` не только подменяет, но и сторожит: если в `proxy-providers:` или в
`proxies:` уходит незакрытое значение — `url`, `server`, `uuid`, `public-key`,
`short-id`, `path` — он завершается с ошибкой и git прерывает коммит. Секрет не
уедет молча. Добавьте значение в `.secrets.yaml` под новым именем и повторите.

## Подписка и автовыбор

Подписка одна. Вторая убрана 27.08.2026 как лишняя — свой узел закрывает то,
ради чего её держали. Автовыбор даёт два разных пула:

| Группа | Как выбирает |
|---|---|
| `Свободный интернет` | быстрейший узел подписки **кроме** семейства `nv` и российских выходов |
| `Подписка` | быстрейший узел подписки без изъятий |

Разница не косметическая: `nv` — самые быстрые узлы, но Google их блокирует
петлёй `GOOGLE_ABUSE`, поэтому из основного пула они исключены. `Подписка`
нужна, когда надо дотянуться именно до них, не выбирая узел руками.

Узлы подписки помечены префиксом `[A] `, чтобы не путались с узлами своего
сервера. При добавлении второй подписки её `path` обязан отличаться, иначе
провайдеры перезапишут файл кэша друг друга.

## Gemini и выход для Google

Google определяет страну не по тому, где стоит сервер, а по своей гео-базе, и
почти всю подписку считает российской. Симптом — Gemini открывается, а потом
показывает заглушку «не поддерживается в вашей стране». По названию узла
вердикт не предсказать: `Poland n1` и `n2` для Google российские, а `n3`, `n4`,
`n6`, `n7` — нет, при одном провайдере и одной стране в имени.

Поэтому выходов два, и путать их не надо:

| Группа | Для чего | Как выбирает узел |
|---|---|---|
| `Google` → `Google-выход` | вся сессия Google: поиск, аккаунты, Gemini, gstatic, аватарки | `fallback` по белому списку проверенных узлов |
| `AI` | Claude, ChatGPT и остальные | любой быстрый нероссийский узел из `Свободный интернет` |

Одной группой это не решается: список под Google — единицы узлов из сотни, и
любой из них может умереть. Пока Claude и Gemini делили группу, смерть такого
узла роняла оба сервиса сразу.

### Обновить белый список

Список стареет при любой замене или переименовании узлов у провайдера. Проверка
одной командой:

    ruby scripts/probe-google.rb

Скрипт спрашивает страну у самого Google через каждый живой узел и печатает
готовую строку `filter:` для группы `Google-выход` — её остаётся вставить в
`config.yaml`. Полезные ключи: `-f 'Poland|Germany'` — проверить только часть
узлов, `-g Twitch` — взять другую группу-пробник, `MIHOMO_API=…` — другой адрес
роутера.

Пробный запрос идёт на `www.youtube.com`: в его HTML есть `"GL":"XX"` — та же
гео-база, что у Gemini. Скрипт переключает **группу YouTube**, а не `AI`, чтобы
не рвать на время проверки Claude, ChatGPT и Gemini; выбранный узел он
возвращает на место, в том числе по Ctrl-C. Если роутер отвалится посреди
прогона, скрипт напечатает команду для ручного восстановления.

## PlayStation через турецкий домашний IP

Группа `PlayStation` первым выходом держит `Турция (резидентский)` — SOCKS5 от
proxy.market с адресом турецкого домашнего провайдера, а не дата-центра. Остальные
выходы группы — запас на случай, если прокси умрёт или кончится трафик.

**Тариф пробный: 100 МБ до 12.11.2026.** Этого хватает на вход в аккаунт и
магазин, но не на загрузку игры: правило `RULE-SET,playstation` ловит и CDN
загрузок, и одна закачка через этот выход съест весь объём за секунды. Перед
скачиванием игр переключите группу на `Выход`.

### Как включить

1. Положить в `.secrets.yaml` три ключа из кабинета proxy.market:
   `TR_RES_SERVER`, `TR_RES_USER`, `TR_RES_PASS`.
2. `scripts/deploy` — он подставит их в конфиг перед отправкой.
3. **Один раз выбрать прокси в группе руками.** `store-selected: true` хранит
   прежний выбор, и порядок в `proxies:` его не перебивает:

       curl -s -X PUT http://192.168.1.1:9090/proxies/PlayStation \
         -d '{"name":"Турция (резидентский)"}'

### Как проверить

С компьютера, минуя роутер (порты 10000–10999 xkeen не перехватывает):

    eval "$(ruby -ryaml -e 's=YAML.load_file(".secrets.yaml"); %w[TR_RES_USER TR_RES_PASS TR_RES_SERVER].each{|k| puts "#{k}=#{s[k].dump}"}')"
    curl -s -x "socks5h://$TR_RES_USER:$TR_RES_PASS@$TR_RES_SERVER:10000" https://ipinfo.io/json

Ответ должен быть с `"country": "TR"` и провайдером вроде Türk Telekom. Что
выбрано в группе и жив ли прокси с точки зрения mihomo:

    curl -s http://192.168.1.1:9090/proxies/PlayStation | grep -o '"now":"[^"]*"'

Каждая проверка — расход того же пробного объёма, гоняйте её по делу.

### Порт задаёт сессию, но не адрес навсегда

Порт из диапазона 10000–10999 выбирает сессию у proxy.market, а сессия — выходной
адрес. Адрес при этом не вечный: днём 13.10.2026 порт 10000 выходил через
Стамбул, а вечером того же дня — через Анкару, 10001 — сначала Türksat в Анкаре,
потом Türk Telekom в Адане. Страна держится, город и провайдер плавают. Если
PSN начнёт требовать повторный вход или ругаться на смену региона — сменить
`port:` в записи прокси на другой из диапазона.

## Свой выходной узел

Живёт в `node/` — там объявление состояния, скрипты и подробный разбор замеров.
Код версионируется, `node/secrets/` в `.gitignore`: внутри приватные ключи
Reality, UUID устройств и QR с рабочим доступом.

В `config.yaml` узел прописан двумя записями в `proxies:` — входы **XHTTP** и
**Vision** на разных портах и с **разными** донорами SNI, чтобы блокировка
одного имени не уносила оба. Группа `Свой узел` выбирает между ними по скорости.

Одно правило стоит знать, не открывая `node/README.md`, потому что оно
переворачивает обычную логику: **своему узлу противопоказан свой домен и свой
сертификат.** Имя в SNI идёт открытым текстом в первом пакете рукопожатия, и
именно по нему фильтр и решает. Замер 27.08.2026 разделил гипотезы крестом на
четырёх ячейках: обскурное имя обрывалось на первом окне TCP на обоих портах и
обоих транспортах, крупное известное имя на обоих отдавало 10 МБ на 9–13 МБ/с.
Дело не в том, чей домен, а в том, насколько имя заметное — поэтому и «возьму
имя понезаметнее» здесь не защита, а приговор. Прятать узел за бесплатным
планом CDN тоже бессмысленно: те диапазоны душат так же.

Донор поэтому не угадывается, а подбирается замером: `./node/bin/pick-donor`.
Разбор, полные таблицы и грабли — в [`node/README.md`](node/README.md).

## Проверять скачиванием, а не задержкой

Относится и к своему узлу, и к узлам подписок. Узел, который отвечает за 178 мс,
отдаёт `200 OK` и возвращает `101 Switching Protocols`, может не передавать
**ничего**: все эти проверки укладываются в первое окно TCP, ~16 КБ, и слепы к
обрыву потока.

Health-check группы `url-test` меряет именно задержку, поэтому здоровым он
считает и такой узел. Если через группу «подключается, но ничего не грузится» —
качать несколько мегабайт через сам туннель и смотреть на байты и скорость.
Для своего узла это делает `./node/bin/verify`.
