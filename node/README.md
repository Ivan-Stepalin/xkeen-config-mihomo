# Выходной узел для xkeen-config-mihomo

Свой VPS в Hetzner под выходной узел: один Xray, два входа VLESS+Reality и
ничего больше. Панель (3x-ui, Remnawave и подобные) не ставится сознательно —
узел один, состояние объявлено в `node.conf`, а панель это лишний открытый
порт и веб-логин, которые надо охранять.

Собран заново 27.08.2026. Предыдущая сборка с доменом, сертификатом
Let's Encrypt, nginx, WebSocket и Cloudflare снесена целиком: замеры показали,
что она не просто лишняя, а вредная.

---

## Главное, что установлено замерами

### Обрыв следует за именем в SNI, а не за портом и не за транспортом

27.08.2026, крест на четырёх ячейках. Один сервер, один клиент, один и тот же
файл на 10 МБ:

| Вход | Порт | Транспорт | SNI | Результат |
|---|---|---|---|---|
| xhttp | 443 | XHTTP | lucaslucid.com | ~5 КБ, обрыв |
| vision | 2096 | Vision | www.tesla.com | 10 МБ, 10.96 МБ/с |
| xhttp | 443 | XHTTP | www.tesla.com | 10 МБ, 9.04 МБ/с |
| vision | 2096 | Vision | lucaslucid.com | 9.5 КБ, обрыв |

Обскурное имя умирает на обоих портах и обоих транспортах, крупное на обоих
работает. Переменная одна — имя.

Тот же XHTTP через ssh-туннель (то есть с тем же конфигом, но без 443 и без
этого SNI на проводе) отдал все 10 МБ на 12.0 МБ/с. Значит конфиг верен, а
рвётся путь снаружи.

**Отсюда критерий донора: заметное имя с большим собственным трафиком.**
Ранняя версия вывода — «душат свой домен, потому что он свой» — была неполной.
Дело не в собственности, а в известности: обскурный чужой сайт душат так же.

### Сканеры доноров ведут в противоположную сторону

Инструменты класса `Reality-SNI-finder` сканируют соседей по подсети,
вытаскивают имена из их сертификатов и ранжируют по TLS-задержке. Логика —
связка «наш IP + имя из той же подсети» выглядит согласованно. На практике
наверх выходят как раз обскурные микросайты, то есть худшие доноры.

Собственный `bin/scan-sni` делает ровно это и оставлен как инструмент
разведки, но **для РФ его результат применять нельзя**. Донора выбирает
`bin/pick-donor` замером из дома.

Замер 27.08.2026, 9 пригодных кандидатов, прошли 5:

| Имя | Результат |
|---|---|
| www.samsung.com | прошёл |
| www.nvidia.com | прошёл |
| www.tesla.com | прошёл |
| www.yahoo.co.jp | прошёл |
| www.intel.com | прошёл |
| www.microsoft.com | обрыв |
| www.icloud.com | обрыв |
| www.amd.com | обрыв |
| www.lovelive-anime.jp | обрыв, 13 736 байт |

Пригодность имени видна с узла (TLS 1.3, ALPN h2, группа x25519, валидный
сертификат). Проходимость — только из дома: душат путь «дом → узел», а не
«узел → донор». Поэтому этапа два, и второй обязателен.

### ТСПУ с июня 2026 смотрит на поведение, а не на протокол

Разборы схемы описывают три сигнала, соединённых через И: подсеть/ASN сервера
(Hetzner в списке подозрительных), TLS-фингерпринт (chrome помечен, firefox у
большинства операторов проходит) и **больше трёх параллельных TLS к одному имени
за 350-400 мс**. Срабатывание — 120 секунд blackhole, не RST; смена
фингерпринта под нагрузкой добавляет 600 секунд.

Отсюда два решения в этой сборке:

* `FINGERPRINT=firefox`, а не chrome;
* основной вход — **XHTTP в режиме stream-one**, который сворачивает обмен в
  один поток. Health-check группы `url-test` в mihomo открывает пачку
  параллельных соединений, то есть сам нажимает третий сигнал.

### Проверять только скачиванием объёма

Узел, отвечающий за 180 мс, отдающий 200 OK и возвращающий `101 Switching
Protocols`, может не передавать ничего: обрыв наступает ровно на одном
начальном окне TCP, ~16 КБ, а в это окно укладываются и заглушка, и
рукопожатие, и DNS-ответ. Из-за этого `url-test` считал мёртвый узел здоровым.

`bin/verify` качает 10 МБ и печатает байты и скорость. Объём меньше 3 МБ не
годится даже для сравнения имён между собой: BBR не успевает разогнаться, и
все результаты садятся вдвое.

## Что не берём, хотя это «best practice 2026»

| Что | Почему нет |
|---|---|
| VLESS Encryption (ML-KEM-768, `decryption` вместо `none`) | у mihomo сломана: MLKEM768 не согласуется, откат на x509 битый |
| Подписи Reality ML-DSA-65 | ссылки с этими полями большинство клиентов не парсит |
| selfsteal: свой домен + Caddy с настоящим сайтом | замером убито — честное имя в SNI душат |
| CDN перед узлом | диапазоны Cloudflare бесплатного плана душат так же |
| Панель 3x-ui / Remnawave | лишний открытый порт и веб-логин на узел из одного сервера |

## Состав узла

| Порт | Что | Роль |
|---|---|---|
| 443/tcp | VLESS + Reality + XHTTP, `mode: auto` | основной для роутера |
| 2096/tcp | VLESS + Reality + XTLS-Vision | запасной, другой донор |
| 22/tcp | ssh, только с домашнего IP | |

Разные доноры на входах намеренно: если одно имя начнут душить, второй вход
продолжает работать. Свои ключи Reality на каждый вход — по той же причине.

Плюс: NTP (Reality без точного времени не работает), BBR, `unattended-upgrades`,
bittorrent и локальные сети в blackhole, `domainStrategy: UseIPv4` у freedom.

Порт **2087 не использовать** — у мобильного оператора TLS на нём рвётся
целиком (`failed to read client hello` в логе Xray).

## Устройство проекта

Состояние объявлено, а не набирается шагами: `node.conf` плюс
`secrets/clients.tsv` — это всё, что описывает узел, а `bin/apply` приводит
сервер к объявленному. Гонять можно сколько угодно, порядок помнить не нужно.

| Файл | Что |
|---|---|
| `node.conf` | объявление: сервер, порты, доноры, фингерпринт |
| `donors.conf` | кандидаты в доноры и критерий отбора |
| `bin/create` | создать сервер, ключ и файрвол; идемпотентно |
| `bin/check-ip` | годится ли адрес под Google и AI |
| `bin/find-clean-ip` | перебрать адреса, пока не попадётся годный |
| `bin/apply` | привести узел к объявленному состоянию |
| `bin/pick-donor` | подобрать донора: пригодность с узла + замер из дома |
| `bin/scan-sni` | разведка имён по соседям (для РФ неприменимо, см. выше) |
| `bin/client` | `add` / `rm` / `list` / `show` — доступ устройствам |
| `bin/verify` | замер скачивания через туннель |
| `bin/render-config` | собрать `secrets/xray.json` из объявления |
| `lib/render.py` | блоки клиента: ссылки, конфиг роутера, проверочный конфиг |
| `bin/destroy` | удалить сервер; только это прекращает тарификацию |
| `remote/*.sh` | то, что выполняется на сервере |

Один и тот же код собирает блок для `config.yaml`, ссылку `vless://` и
проверочный конфиг. Поэтому `bin/verify` проверяет ровно то, что поедет в
прод, включая имена полей `xhttp-opts`.

### Требования

`hcloud` с активным токеном (`hcloud context create vpn`), `jq`, `qrencode`,
`mihomo` (`brew install mihomo`) и ключ `~/.ssh/id_ed25519`.

### Типовые действия

`bin/apply` первым шагом выставляет файрвол и только потом идёт по ssh: правило
для 22 привязано к домашнему адресу, а его меняет провайдер. В обратном порядке
скрипт падал бы на первом же подключении и не доходил до починки доступа.

```sh
./bin/apply                  # привести узел к node.conf
./bin/verify                 # замер обоих входов
./bin/pick-donor --pin       # пересобрать доноров, если начали душить
./bin/client add laptop      # доступ новому устройству
./bin/client show router     # блок для config.yaml роутера, QR в secrets/
```

Замена адреса, если его засветят:

```sh
./bin/destroy && ./bin/find-clean-ip && ./bin/apply
./bin/client show router     # реквизиты сменились — обновить config.yaml
```

## Грабли, на которые уже наступили

**`minClientVer` обязателен.** Xray 26.x по умолчанию требует клиента не
старше своей версии и отбрасывает остальных до проверки ключей, а mihomo
объявляет себя REALITY-клиентом 1.8.2. Без `"minClientVer": "1.8.0"` узел не
подключится, а на клиенте будет только `REALITY authentication failed`.

**Конфиг Xray нельзя класть с правами 600 root:root.** Служба работает под
`nobody` и падает с `permission denied`. Нужно `root:nogroup` и `640`.

**Временный файл конфига обязан кончаться на `.json`.** Формат Xray берёт из
расширения, `config.json.new` даёт `failed to get format`.

**`hcloud firewall replace-rules --rules-file -` не читает stdin** и висит без
таймаута. Только через настоящий файл.

**`openssl s_client -brief` не печатает ни ALPN, ни группу обмена ключами.**
Группу читать из `Server Temp Key`, а h2 подтверждать curl по
`%{http_version}`.

**Узел нельзя проверять с машины за этим же роутером.** В `config.yaml`
включён TLS-сниффер с `parse-pure-ip`, и соединение на голый IP с чужим SNI
роутер уводит на настоящий сайт донора: клиент получает подлинный сертификат и
падает с `REALITY authentication failed` при исправном узле. Лечится строкой
`skip-dst-address` с адресом узла — она в конфиге уже есть.

**`speed.hetzner.de` из самого Hetzner не отвечает.** Для замеров используется
`speed.cloudflare.com`.

**Имена узлов без префикса `[S] `** — его добавлял провайдер подписки, которого
больше нет.

## Тарификация

Почасовая с месячным потолком, цены нетто: `cx23` €6.49/мес плюс primary IPv4
€0.60 — итого €7.09 нетто, €8.58 с НДС 21%. **Выключенный сервер тарифицируется
полностью**, деньги останавливает только удаление. Включённые 20 TB исходящего
выбрать невозможно.

Личный VPN правилам Hetzner не противоречит, но на abuse-жалобы они реагируют
блокировкой без разговоров — поэтому торрент в blackhole, а порт 25 закрыт у
Hetzner по умолчанию.

## Секреты

`secrets/` целиком в `.gitignore`: там приватные ключи Reality, UUID устройств
и собранный конфиг Xray. Сам код проекта версионируется.

Реквизиты узла в `config.yaml` роутера подставляются smudge-фильтром из
`.secrets.yaml`, а clean-фильтр на `git add` заменяет их плейсхолдерами.
Страховка в `scripts/scrub.rb` останавливает коммит, если в `proxies:` или
`proxy-providers:` уходит незакрытое значение.
